# 画面設計の原則（大迫の指摘から）

正本は `~/mono-hq/.claude/skills/ui-design-principles/SKILL.md`。各リポジトリの同名スキルは複製なので、変えるときは正本を直して全リポジトリへ同じ内容を配る。Codex 向けの要約は `~/.codex/AGENTS.md` と `~/.claude/CLAUDE.md` の「画面設計の原則」節にある。

## 前提にする利用者

**初めて触る短期の作業者（タイミー等）でも、説明なしで作業を終えられること**を基準にする。社内の担当者や開発者が使える、では合格にしない。

## 原則

1. **UI/UX は最小限にする。** 画面に出す要素は「今この作業に要るもの」だけにする。機能は減らさずに、見せる数を減らす。
2. **ボタンを減らす。** 1 つの画面・1 つの行で目立つのは主ボタン 1 つだけにする。それ以外の操作は「⋯」メニュー・⚙・折りたたみに入れる。まとめて操作するボタンは、対象を選んだときだけ出す。
3. **見て分かる・ごちゃごちゃさせない。** 状態表示は 1 か所・1 本にまとめ、今の状態に合わせて入れ替える（例: つながっている／ログインしてください／停止中＋再開／要確認 N 件）。同じ意味の表示を複数の場所に出さない。
4. **準備作業を利用者にさせない。** CSV の読み込み・キーやトークンの入力・初期設定は、作る側が事前に済ませておく。URL を開く（アプリを起動する）だけで作業を始められる状態を完成とする。特にスマホで長い文字列を入力させない。
   - 秘密のキーは公開ページやアプリに埋め込まない。サーバー側に置き、画面からはサーバー経由で使う。そのうえで書き込める範囲を絞る。
5. **社内用語・内部 ID を画面に出さない。** 利用者が知らない言葉（例: 社内の略号・管理コード）は、やることが分かる言葉に置き換える。
6. **最初の一歩を一番大きく置く。** 画面を開いて最初に押すもの（例:「箱のバーコードを読む」）を最上部に大きく置く。絞り込み・検索・詳細設定は折りたたむ。
7. **使い方は初回だけ短く出す。** 3 行程度にする。保存できたか・つながっているかなど、利用者が不安になる状態は常に見える位置に出す（例:「保存済み ✓」）。

## 設計・レビューでの確かめ方

画面を持つ変更では、設計書と PR 本文に次を書く。満たせない項目は理由を書く。

- 想定する利用者（初見の短期作業者で通るか）
- 画面を開いてから作業完了までに押す回数と、利用者が入力する項目（準備作業が残っていないか）
- 1 画面・1 行で目立つボタンの数（主ボタン 1 つか）
- 画面に出る社内用語の有無
- 入口（LP・ポータル・メニュー）から押して目的の画面に着くこと（全体ルールの導線確認と同じ）
